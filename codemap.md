## Project Responsibility
LTX-Desktop is an Electron desktop application for **local/offline AI video generation using LTX-2.x models** (text-to-video, image-to-video, audio-to-video, IC-LoRA workflows, retake, and image generation). It wraps a Python FastAPI ML backend that orchestrates Lightricks `ltx_pipelines` + HuggingFace GGUF/Kijai/local transformer profiles, behind a React renderer and an Electron main process that supervises the backend lifecycle, IPC, and ffmpeg-based timeline export.

Three-layer architecture:
- **Frontend** (`frontend/`): React 18 + TypeScript + Tailwind renderer.
- **Electron** (`electron/`): Main process — app lifecycle, window, IPC bridge, Python-backend supervision, ffmpeg export.
- **Backend** (`backend/`): Python 3.13 FastAPI server (dev port `41954`, documented `8000`) handling ML model orchestration and generation.

## Core Architectural Conventions
- **Backend request flow**: `_routes/* (thin plumbing) → AppHandler → handlers/* (logic) → services/* (side effects) + state/* (mutations)`.
- **State**: centralized `AppState` with **discriminated-union** state machines (`GenerationRunning | Complete | Error | Cancelled`, plus HF-auth, download, GPU-slot pipeline unions).
- **Concurrency**: thread pool + shared `RLock`. Pattern: `lock → read/validate → unlock → heavy work → lock → write`. **Never hold the lock during heavy compute/IO.**
- **Services**: Protocol interfaces with real + `Fake*` test implementations (`ServiceBundle`). The test boundary for GPU/network side effects.
- **Exception handling**: boundary-owned traceback policy. Handlers raise `HTTPError(..., )` with `from exc` chaining; `app_factory.py` owns logging. No `logger.exception()` then rethrow.
- **Naming**: `*Payload` = DTO/TypedDict, `*Like` = structural wrapper, `Fake*` = test impl.
- **Frontend state**: React contexts only (`ProjectContext`, `AppSettingsContext`, `KeyboardShortcutsContext`, `ViewContext`). `zustand` is in deps but used **only inside the editor store** (`frontend/views/editor/editor-store.tsx`), not for global app state.
- **Frontend→backend HTTP**: always `backendFetch` from `frontend/lib/backend.ts` (attaches auth/session). Never raw `fetch` to app backend.
- **Frontend→Electron**: always `window.electronAPI` (typed via `shared/electron-api-schema.ts` → `InvokeAPI` mapped type).
- **Testing**: backend integration-first via Starlette `TestClient` against the real FastAPI app; **no mocks** (`test_no_mock_usage.py` enforces), swap services via `ServiceBundle` fakes. Pyright strict mode is also a test (`test_pyright.py`). No frontend tests exist.
- **OpenAPI**: backend schema is the source of truth; `openapi:generate` exports JSON + regenerates `frontend/generated/backend-openapi.{json,ts}`; `openapi:check` asserts no drift in CI.

## Key Data & Control Flow (end-to-end generation)
1. User configures a generation in the renderer (e.g. `GenSpace.tsx` → `PromptBar`; `ICLoraPanel.tsx` for IC-LoRA).
2. A hook (e.g. `use-ic-lora.ts`) builds a typed request and POSTs via `backendFetch` → app backend.
3. `backend/_routes/<domain>.py` parses input, calls the matching `AppHandler` method.
4. `AppHandler` (under `RLock`) validates + transitions `AppState`, then dispatches to a domain handler (`ic_lora_handler`, `video_generation_handler`, …).
5. Handler selects a pipeline service (`ServiceBundle`), runs heavy GPU work off-lock, then re-locks to write terminal state.
6. Pipeline decodes frames and encodes output via `services/ltx_pipeline_common.py::encode_video_output()` → `ltx_pipelines.utils.media_io.encode_video` (**H.264/yuv420p hardcoded**, `.mp4` path). `retake_pipeline` bypasses this with a direct call.
7. Output path returned to renderer; Electron serves media via a custom protocol; optional ffmpeg timeline export via `electron/export/`.

## Integration Points Worth Knowing
- **Encode chokepoint**: `backend/services/ltx_pipeline_common.py::encode_video_output()` is the single shared encode path for all video pipelines except retake. Any primary MOV-ProRes/EXR work must thread codec/profile/pixel-format/dims through here AND fix `retake_pipeline`'s direct call.
- **Hardcoded `.mp4`**: `video_generation_handler.py`, `ic_lora_handler.py`, `retake_handler.py` construct output paths as `.mp4`.
- **Proxy precedent**: `electron/ipc/file-handlers.ts::transcodeVideoInPlace` and `electron/export/export-handler.ts` ProRes blocks inform a keep-primary + proxy-sidecar design (frontend `<video>` cannot play EXR; ProRes playback is OS-dependent).
- **HDR (implemented, one-stage)**: `LTXHdrIcLoraPipeline` subclasses upstream `HDRICLoraPipeline` and overrides `__call__` to run a **single full-resolution stage-1 pass → chunked decode/LogC3 → EXR/proxy** (no upsampler, no stage-2 re-sampling). `stage_2`/`upsampler` remain constructed by `__init__` (component-patch helpers expect the attrs) but are never called by the one-stage `__call__`. `_create_conditionings` is called once at full aligned resolution; `_decode_video` is overridden for chunked decode + per-chunk HDR postprocess with immediate CPU handoff. HDR is a supported V2V workflow: `ic_lora_handler` ignores prompt/audio/`conditioning_type`/`images`, requires a source video (uses the source video's original path), never rejects by frame count, accepts **dev, distilled, split, Kijai, and GGUF** component builds (rejects only `base_family == "unknown"` with `UNSUPPORTED_MODEL_BASE_FAMILY`), forwards `scene_embeddings_path`, and returns `video_path` (EXR dir) + `proxy_path` (SDR MP4). Model selection changes **only the main transformer**; sidecar components (VAE/text-encoder/etc.) stay componentized. A dev base requires a distilled LoRA applied @ 0.5 before the HDR LoRA @ 1.0; a distilled base applies the HDR LoRA only (no distilled LoRA). The frontend allows an empty HDR prompt and keeps EXR `videoPath` as the primary asset with `proxyPath` as the preview sidecar. IC-LoRA/HDR generation now reuses the same live progress/metrics polling (`getGenerationProgress` every 500ms) as normal T2V generation. **Remaining-gated**: real-model numeric parity / non-flat EXR / no-clamp linear-HDR validation requires a separate exact harness (Phase 6b), not yet defined.
- **State machines**: `backend/state/app_state_types.py` — extend discriminated unions when adding new generation/output kinds.
- **Phase 1 trace/harness (observational, env-gated)**: `backend/services/memory_trace.py` is a JSONL memory profiler gated on `LTX_MEMORY_TRACE_PATH` — every entry point no-ops (no torch/psutil import, never raises) when unset; enabled, it lazily samples CUDA + RSS with run/case context (`MemoryTraceContext`, `use_context`), `phase()`/`snapshot()`/`reset_peak()`/`write_event()` helpers. `app_factory.create_app()` installs an HTTP trace middleware emitting `http_start`/`http_end`/`http_error` events (terminal deduped via a request-state flag, surviving `BaseHTTPMiddleware` task isolation) plus terminal events in the four exception handlers — only when trace env is set. `pipelines_handler` and the service pipelines (load/create/HDR/encode/GGUF/manual-drain sites) emit `phase_*`/`manual_drain` events purely as diagnostics; zero behavior change when disabled. `backend/scripts/live_workflow_test.py` is an out-of-band stdlib-only harness that **spawns** (`--backend auto`, owning `report.json`/`summary.md`/`backend.log`/trace truncation once) or **attaches** to a running backend, preflights settings/profile, exercises the Phase 1 contracts, and validates output + trace ownership per case; `harness:selftest` is a no-generation `GET /health` case.
- **Adaptive memory/performance policy (HDR-first, intended to generalize)**: `backend/services/block_offload.py` provides block-level offload combining static GPU residency (first N transformer blocks resident, unhooked) with rolling blockswap/prefetch (offloaded groups prefetched CPU→onload on a side CUDA stream and evicted after use; race-free via stream events). Residency/prefetch/look-behind and HDR VAE encode/decode tiling are chosen by a **runtime policy from detected CUDA VRAM + padded frame count**, not fixed tiers: resident blocks follow a monotonic VRAM curve (≈12/16/24/31 GiB → 0/26/37/46 blocks); encode tiling is policy-driven (31GiB: ≤121f no tile, >121f tile512; lower VRAM tiles earlier, with a direct→tiled OOM fallback); decode tiling is fixed at spatial 512/overlap 128 and runs chunked decode + per-chunk HDR `LogC3` postprocess with immediate CPU chunk handoff (avoids the full-video GPU postprocess OOM on 201-frame Kijai/GGUF). All are overridable via env knobs for benchmarking (`LTX_BLOCK_OFFLOAD_RESIDENT_BLOCKS`/`_PREFETCH_GROUPS`/`_LOOKBEHIND_GROUPS`, `LTX_HDR_VAE_TILE_SIZE`/`_THRESHOLD`, `LTX_HDR_DECODE_VAE_TILE_SIZE`, `LTX_HDR_PADDED_FRAMES`). Computed values are traced (`block_offload_apply`/`build`, `hdr_encode_policy`). **Rolling temporal context windows are on by default for one-stage HDR** (`LTX_HDR_CONTEXT_WINDOW=0` disables) because full 201-frame full-res one-stage OOMs even with all blocks streamed; defaults are VRAM-based (measured RTX 5090/31GiB: 65-frame window, 16 overlap, pyramid fuse — passes Kijai/GGUF 201f with 46 resident / 2 swapped blocks; 73-frame window failed at 46 and 42 resident; provisional lower-VRAM defaults: 49/16 ≥24GiB, 33/8 below/unknown, pending hardware validation). This lives in the HDR wrapper today but is the intended shape for a shared memory/model-management layer reusable by the other generation workflows later.
- **Generation output folder enforcement**: when `AppSettings.projectAssetsDir` is set, all backend generation outputs/intermediates (EXR/MP4/ProRes/image/control temp) resolve via `StateHandlerBase.outputs_dir` to `<projectAssetsDir>/.ltx-generations` (a hidden subfolder, created on demand) so Electron/project copying can organize final assets into per-project folders without source/dest collision. Unset → falls back to `RuntimeConfig.outputs_dir`. The frontend `SettingsModal` syncs the Electron project-assets path to backend `projectAssetsDir` (on modal open + on user change). `modelsDir` behavior is unchanged.
